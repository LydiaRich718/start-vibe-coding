Git basics

Section 11 of the course covers the two moves you need on day one. This page covers what comes after, for when you are building something you care about.

The mental model

Git keeps a list of commits. Each commit is a complete photograph of every file in your project at one moment, plus a short note saying what changed. The list only grows. Nothing you commit is ever really lost, which is the whole reason the thing exists.

A commit is a photograph.
Your history is the album.

Everything below is a way of moving around that album, or of keeping two albums in step with each other.

The six things worth knowing

You will say these to Claude in English. The command is there so the word means something when you see it.

1. Commit

Take the photograph. Do this whenever something works, before you try anything ambitious.

Say
This works. Commit it as a save point.

2. Push and pull

Push sends your commits up to GitHub. Pull brings down commits that are on GitHub but not on your machine. If you only ever work on one computer, alone, you will push often and pull almost never.

Say
Commit this and push it to GitHub.

3. Status and diff

Status answers "what have I touched since the last commit?". Diff answers "and what exactly changed in those files?". These are how you find out what is going on before you decide anything.

Say
What has changed since my last commit? Show me in plain English.

4. Going back

The reason for all of this. You can return to any commit in the album. Ask for it in words and let Claude choose the safe way to do it, because there are several and some of them throw work away.

Say
Something is broken. Take me back to the last commit that worked, and explain what was different about it.

The one to be careful with

A command called git reset --hard can delete work that was never committed. If Claude proposes it, ask what will be lost before you agree. Anything already committed is safe; anything you typed since is not.

5. Branches

A branch is a second album, started from a photograph in the first. You try something risky on the branch, and your working version stays untouched the whole time. If the experiment succeeds you merge it back. If it fails you delete the branch and nothing was ever at risk.

Say
I want to try something that might not work. Put me on a new branch for it, and remind me how to get back.

6. Conflicts

When two branches changed the same line of the same file, Git refuses to guess and asks you to choose. That is a merge conflict. It is not a breakage, it is a question. Working alone you will rarely see one.

Say
I have a merge conflict. Explain which two versions are fighting and what each one does, then help me pick.

Habits that make Git worth having

Commit smaller and more often than feels necessary

A commit holding one change can be undone precisely. A commit holding a day of changes can only be undone by losing the day.

Write the note as though somebody will read it

Six months from now, that somebody is you, and "fixed stuff" will tell you nothing.

Push at the end of every session

Work that exists only on your laptop is one spilled drink away from not existing.
